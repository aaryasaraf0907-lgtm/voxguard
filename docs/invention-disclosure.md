## 1. Title

Codec-aware training, calibration and evaluation of voice-deepfake detection for telephone
audio, with a call-level prevention layer.

## 2. Problem

Voice-cloning ("vishing") scams reach victims over the telephone network. Before a detector sees
the audio, the call has passed through lossy speech codecs (AMR-NB/WB on mobile networks, G.711
on fixed lines, GSM full-rate, low-bitrate Opus on VoIP). These codecs band-limit the signal to
about 3.4 kHz (narrowband) or 7 kHz (wideband), quantise it coarsely and discard fine spectral
detail.

Most published deepfake-speech detectors are trained and benchmarked on clean 16 kHz studio
speech (for example ASVspoof 2019 LA). Their decision cues often live in exactly the detail that
codecs remove, so accuracy measured in the lab overstates accuracy on real calls. A second,
less discussed problem is the **operating point**: a threshold chosen on clean audio can sit in
the wrong place for codec-degraded audio, so a detector with a reasonable EER still mislabels
calls at deployment. Our own clean-trained SSL-AASIST model shows this: its EER threshold on
clean audio differs from the one on phone-degraded audio, and the conventional 0.5 threshold is
unusable (see the SSL-AASIST preview in `docs/STATUS.md`; final numbers will be in
`docs/results.md`).

## 4. Technical solution

### 4.1 Telephony-channel simulation (training data)

For every training clip (16 kHz mono) we keep the clean version and generate N randomised
telephone-channel variants (N = 2 in the current run, giving 76,140 training rows from 25,380
clips). Each variant applies, in order:

1. optional additive noise (probability 0.3, SNR uniform in 10-30 dB);
2. resampling to the codec's native rate (8 kHz for narrowband codecs, 16 kHz for wideband);
3. a real encode-decode round trip through a standard codec implementation (FFmpeg), with the
   bitrate drawn from that codec's legal set:
   - G.711 mu-law and A-law (64 kbit/s);
   - AMR-NB (4.75-12.2 kbit/s, 8 modes); AMR-WB (6.6-23.85 kbit/s, 9 modes);
   - GSM full-rate (13 kbit/s);
   - Opus (6-24 kbit/s);
4. resampling back to 16 kHz.

The random choice for each (file, variant index) is derived from `sha256(seed, path, index)`,
so the dataset is bit-for-bit reproducible regardless of processing order or parallelism, and
every row in the manifest records its codec and bitrate. Variants are precomputed offline once
instead of encoding on the fly, which keeps GPU training free of subprocess overhead.
Implementation: `src/voxguard/data/codecs.py`, `src/voxguard/data/augment.py`,
`configs/codecs.yaml`.

### 4.2 Detector and training

SSL-AASIST: a multilingual self-supervised front end (XLS-R 300M, fine-tuned) feeding an AASIST
graph-attention back end, trained with class-weighted cross-entropy on the mixed clean +
codec-variant data. RawNet2 trained from raw waveform is the baseline. The architecture is
published prior work and is **not** claimed. Training detail that mattered in practice: under
mixed precision, a single non-finite forward pass can corrupt BatchNorm running statistics even
when the optimizer step is skipped; we skip such batches and restore the statistics
(`train_step` in `src/voxguard/train.py`).

### 4.3 Codec-aware evaluation protocol

Each model is scored on the same eval clips under clean audio and under one deterministic
degraded copy per codec, giving:

- the **2x2 matrix**: {trained clean, trained codec-augmented} x {tested clean, tested
  phone-degraded};
- a per-codec breakdown of the degraded column;
- a **held-out codec** (GSM) that no training run saw, to test generalisation to unseen
  channels;
- latency per 4 s clip (p50 / p95) on CPU and GPU, since the use case is live calls.

### 4.4 Candidate distinguishing features (for discussion with the IPR cell)

None of these is established as novel; each needs a targeted prior-art search.

1. **Channel-matched operating point.** The decision threshold is calibrated on codec-degraded
   audio, not clean audio, and stored with the model so the deployed service applies it
   automatically. Planned: optionally one threshold per detected channel type.
2. **Call-level prevention loop.** A detection at or above the threshold flags the session,
   raises an alert and upserts the caller ID into a blocklist with a hit counter; a second
   operating mode (`low_far`) shifts the threshold to reduce missed fakes. The detector and the
   blocking action form one telephone-call screening system (`src/voxguard/api/prevention.py`; threshold modes in `src/voxguard/api/deps.py`).
3. **Reproducible, recorded channel augmentation.** Hash-seeded per-file codec/bitrate/noise
   draws with the channel recorded per training row, which makes per-codec ablations and
   held-out-codec tests exact. (Likely weak alone; useful as a dependent feature.)
4. **"Same call, two channels" demonstration.** The service can re-encode an uploaded clip
   through a chosen codec and score both versions side by side. (Probably a demo feature, not
   claimable.)

**What the RawNet2 results show so far, stated plainly.** Codec augmentation reduced the pooled
phone-degraded EER and made the largest difference on AMR-NB, the harshest narrowband codec.
It also raised the clean EER and the G.711 and Opus EERs, and it did **not** improve the
held-out GSM codec. So the expected effect is only partly shown for the baseline. The
disclosure must report this as measured. The SSL-AASIST codec-augmented run is the main test of
the effect.
